# Connect the RCM Lab training spreadsheet

The spreadsheet structure is prepared. The website is not connected yet. This script is a storage adapter, not the payer simulator itself. It needs deployment and live testing before learner use.

## What you do in Google

1. Open your RCM Lab Training Sessions spreadsheet. Choose **Extensions → Apps Script**.
2. Replace the sample code with the contents of **RCM_Lab_Storage.gs** and save. The supplied code already names your spreadsheet.
3. In **Project Settings → Script Properties**, add **RCM_STORAGE_KEY** with a unique randomly generated secret of at least 32 characters. Keep it private. It must later be entered into the Lab's private server configuration with the name **RCM_STORAGE_KEY**. Do not paste it into chat, spreadsheet cells or learner-facing code.
4. Choose **Deploy → New deployment → Web app**. Set **Execute as: Me**. The Lab's server needs to reach the endpoint without a learner Google login, so select **Who has access: Anyone**, if your Google account permits it. This makes the endpoint reachable, not the spreadsheet public; reads and writes require the private key and the learner's private resume code. If your organization prohibits this deployment setting, pause here and report that restriction.
5. Complete Google's authorization flow yourself. Review the spreadsheet access requested. Do not bypass a browser security warning. If you are unsure about an authorization screen, stop and share its non-secret wording.
6. Copy the **Web app URL ending in /exec** and send that URL in this chat. Keep the spreadsheet private. Do not send your Google password or the storage key.

## What will be connected in the Lab

The private server configuration needs **RCM_STORAGE_URL** (the /exec URL) and **RCM_STORAGE_KEY** (matching the Script Property). The Lab backend must generate high-entropy resume codes, keep the storage key server-side, limit requests, and validate the learner session before forwarding data. This configuration and website integration are still pending. Connecting Google Drive to this chat does not automatically authorize a running website.

The client will batch research events, show saving/pending/failed status, keep unsent work locally, and retry identical requests after connection failures. Revision conflicts must prompt a refresh or reconciliation rather than overwrite another tab's newer work. Resume codes must be treated as private access codes; the Sheet stores only their hashes. No readable resume codes or real patient data belong in this spreadsheet.

## Stored records

- **Sessions:** learner name, code hash, version and timestamps.
- **Case Progress:** per-case saved state and revision.
- **Research Log:** portal, phone and chat events, with unique event identifiers.
- **Submissions:** selected fictional documents and submission acknowledgments. An acknowledgment is not an approval or payment.
- **Setup:** connection status and facilitator instructions.

PDFs are generated by the Lab for learners to download. Automatic PDF upload to Drive is not included. The script contains no delete operation and does not expose worksheet rows through its public status page.

## Verification before rollout

Confirm a test learner can save and resume; a wrong code cannot read another session; repeated requests do not duplicate interactions; two tabs cannot overwrite newer revisions; pending work survives a connection failure; and the final PDF includes the synchronized payer record. Offline adapter checks do not replace a deployed Google integration test.
